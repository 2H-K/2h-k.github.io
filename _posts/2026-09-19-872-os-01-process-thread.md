## 2. 进程的概念与组成

### 必背

- **进程**是进程实体的**运行过程**，是系统进行**资源分配和调度的独立单位**。进程实体（进程映像）= **PCB + 程序段 + 数据段**。
- 创建进程实质上是创建进程的PCB，撤销进程实质上是撤销PCB——**PCB是进程存在的唯一标志**。
- **动态性是进程最基本的特征**：程序是静态的指令集合、可长期保存；进程是程序的一次执行，有诞生和消亡。

进程五大特征：**动态**性（最基本）、**并发**性（宏观同时运行）、**独立**性（资源分配与调度的独立单位）、**异步**性（按不可预知速度推进）、**结构**性（进程实体三段式）。

### PCB 的内容（四类，选择高频）

| 类别 | 具体内容 |
|---|---|
| 进程标识信息 | 进程 PID、父进程 PID、用户 ID |
| 处理机状态（现场） | PC 程序计数器、PSW 程序状态字、通用寄存器、栈指针——切换时保存/恢复的就是这些 |
| 进程调度信息 | 进程状态、优先级、等待事件、调度队列指针 |
| 进程控制信息 | 程序段/数据段地址、资源清单（打开文件、内存分配）、同步通信信息、PCB 链接指针 |

PCB 的组织方式：**链接方式**（按状态把 PCB 链成就绪/阻塞等队列）、**索引方式**（按状态建索引表，表项指向 PCB）。【辨析】

### 程序 / 进程 / 作业

| 对比项 | 程序 | 进程 | 作业 |
|---|---|---|---|
| 存在形态 | 静态指令集合，存于磁盘 | 程序的一次动态执行 | 用户提交的任务（程序+数据+作业说明书） |
| 资源 | 不拥有 | 拥有资源，是资源分配单位 | 被高级调度选中后才建进程、获资源 |
| 关系 | 一个程序可对应多个进程 | 一个作业可对应多个进程 | 批处理术语，生命周期 = 提交→完成 |

> 作业调度（高级）把作业从外存选入内存并建进程；进程调度（低级）才决定进程谁上 CPU。

## 3. 进程状态与转换

### 3.1 状态模型的演进：2 态 → 3 态 → 5 态

进程状态模型是随管理需要逐步细化的，三层模型包含关系要先理清：

| 模型 | 状态组成 | 为什么这样分 |
|---|---|---|
| **两状态模型**（最简单） | **运行态、非运行态** | 早期调度只回答"CPU 给谁"：占用 CPU 的进"运行态"，其余全部排队等在唯一的"非运行态"，不区分等待原因 |
| **三状态模型**（核心） | **运行态（执行态）、就绪态、阻塞态（等待态）** | 非运行态里的进程"不能运行"有两种本质不同的原因：一种是**只差 CPU**，一种是**在等 I/O/事件、给了 CPU 也跑不了**——拆开才有了就绪与阻塞 |
| **五状态模型** | 三态 + **创建态（新建态）** + **终止态（结束态）** | 三态没描述进程的"出生和死亡"：进程被创建、PCB 已分配但尚未进入就绪队列的阶段 = 创建态；执行结束、PCB 待回收的阶段 = 终止态 |

- **就绪态**：获得了除 CPU 外的一切资源，只差调度
- **运行态**：已获 CPU，正在执行（单处理机同一时刻只有一个）
- **阻塞态**：因等待某事件（I/O、P 操作、其他资源）而暂停，给了 CPU 也不能运行

![进程五状态的转换（含资源判定与主动/被动说明）](/assets/img/csreview/process-status.png)

转换判据（选择题必考，按"主动/被动"判）：

| 转换 | 触发 |
|---|---|
| 创建→就绪 | OS 完成创建进程的一系列工作（分配 PCB、初始化资源），加入就绪队列 |
| 就绪→运行 | 唯一原因：**进程被调度**，获得 CPU |
| 运行→就绪 | **被动**：时间片到，或被更高优先级进程抢占 |
| 运行→阻塞 | **进程主动**：以系统调用方式申请资源未满足、请求等待某事件、执行 P 操作（02 篇） |
| 阻塞→就绪 | **被动**：申请的资源被分配或等待的事件发生，被唤醒（通常在中断处理中完成） |
| 运行→终止 | 运行结束，或遇到不可修复的错误 |

> 两条"死路"必须记住（图底部红字）：**阻塞不能直接到运行**（必须先就绪）；**就绪不能直接到阻塞**（进入阻塞是进程在运行中主动发起的请求，就绪态根本没在执行）。
>
> 图中"处理机 × / 其他资源 √"是各状态的资源画像：**就绪** = CPU 没有、其他资源都有；**运行** = CPU 和其他资源都有；**阻塞** = CPU 和所等资源都没有；阻塞被唤醒后先回就绪而不是直接运行，正是因为它要重新排队等 CPU。

### 3.2 七态：五态再引入挂起

挂起 = 进程映像被**换出到外存**对换区（内存紧张时的调节手段），新增**就绪挂起、阻塞挂起**两态，对应的调入/调出即**中级调度**。

| 对比项 | 阻塞（等待） | 挂起 |
|---|---|---|
| 原因 | 等待某事件发生 | 被系统换出（负载调节）/ 用户请求 |
| 映像位置 | **仍在内存** | 换到**外存**对换区 |
| 恢复路径 | 事件到 → 就绪 | 先由中级调度换回内存（阻塞挂起者事件到时先变就绪挂起） |
| 进程视角 | 主动 block | 被动 suspend |

关键转换边：就绪⇄就绪挂起、阻塞⇄阻塞挂起（挂起/激活原语）；阻塞挂起上事件发生 → **就绪挂起**（不是直接回内存）。

## 4. 进程控制与上下文切换

### 原语（【必背】）

进程控制由**原语**完成。原语是**原子操作**，执行期间不可中断，靠在内核态**关中断**实现。

| 原语 | 动作要点 |
|---|---|
| 创建 create | 申请空白 PCB → 分配资源 → 初始化 PCB → 插入就绪队列。允许父进程创建子进程形成进程树 |
| 终止 terminate | 回收资源、撤销 PCB；触发：正常结束 / 异常（越界、非法指令、算术错）/ 外界干预（kill） |
| 阻塞 block | **进程自己执行**：运行态 → 插入阻塞队列；与 wakeup **成对** |
| 唤醒 wakeup | 事件发生时由**其他进程或 OS（通常在中断处理中）**执行：阻塞队列 → 就绪队列 |
| 切换 switch | 保存现场到当前 PCB → 改状态入队 → 选下一进程 → 从其 PCB 恢复现场 |

> 易错锚点：阻塞进程自己不可能唤醒自己（它已经不运行了）。

### 上下文切换

- **上下文**：PC、PSW、通用寄存器、栈指针等硬件现场（存在 PCB），外加页表基址等系统上下文。
- 一次进程切换的实际开销：保存/恢复寄存器、**切换页表导致 TLB 失效**、Cache 冷启动，可能比保存几条寄存器贵得多。

| 对比项 | 模式切换 | 进程切换 |
|---|---|---|
| 含义 | 同一进程在用户态↔内核态间切换（中断、系统调用） | 当前进程让出 CPU，换上另一个 PCB |
| 开销 | 小，只换硬件特权级和栈 | 大，保存/恢复现场、切地址空间 |
| 关系 | 系统调用/中断必有模式切换，但**不一定**换进程 | 进程切换通常经内核完成，必含模式切换 |

> 中断处理结束后不一定回到被中断的进程：若时间片已到，调度程序可让另一个进程先运行。

## 5. 进程间通信（IPC）

| 方式 | 机制 | 高频考点 |
|---|---|---|
| **共享存储** | 在内存划一块共享区，各进程直接读写该区域交换数据 | 必须靠**互斥同步（PV）**协调访问；分基于数据结构（低级）与基于存储区（高级）；**速度最快** |
| **消息传递** | 以格式化的**消息**为单位，用 send/receive 两个原语 | 直接通信（指明对方）/ 间接通信（**信箱**）；无需共享变量，靠内核转发 |
| **管道通信** | 连接读进程与写进程的一个共享文件（**字符流的队列**） | **半双工、单向**；固定大小缓冲区，写满则写者阻塞、读空则读者阻塞；数据读出即被移走；通常用于有**血缘**关系的进程 |

一句话辨析：共享存储靠"共同空间 + 自己加锁"；消息传递靠"内核收发报文"；管道是"先进先出的字节流，单向传输"。要双向通信就建**两个**管道。

## 6. 线程

### 必背

- **线程**是进程内一个相对独立的、可被 OS 调度分派的执行单元（轻量级进程）。引入目的：**减小并发执行的时空开销，提高并发度**。【必背】
- 在引入线程的系统中：**进程是资源分配的基本单位，线程是调度（CPU 分派）的基本单位**。【必背】

### 共享 / 私有表 ★（02 篇所有 PV 题的共享变量从这张表查）

| 同进程内多线程**共享** | 各线程**私有** |
|---|---|
| 进程地址空间（代码段、数据段、**堆**） | 线程 ID、线程控制块 TCB |
| 全局变量、静态变量 | **栈**（局部变量、函数调用链、参数返回值） |
| 打开的文件表、当前工作目录 | PC、PSW、通用寄存器等处理机现场 |
| 信号处理函数、用户 ID/组 ID | 线程局部存储 TLS、线程自身的信号掩码/errno |

> 一句话：**堆共享、栈私有**。同进程线程间通信可直接读写全局变量——但正因为如此才需要 02 篇的互斥。

### 用户级线程 vs 内核级线程

| 维度 | 用户级线程 ULT | 内核级线程 KLT |
|---|---|---|
| 管理者 | 用户空间的**线程库**，内核看不到线程 | OS 内核 |
| 切换 | 不进内核、无模式切换，**快** | 进内核，开销大 |
| 阻塞问题 | 一个线程发起阻塞式调用，**整个进程被阻塞** | 只阻塞该线程，同进程其他线程仍可运行 |
| 多核并行 | 不能（内核只看到一个执行流） | 能并行到多个 CPU |
| 创建/撤销 | 库函数完成，开销小 | 系统调用完成，开销大 |

### 三种映射模型 ★（考研重点，逐模型过）

ULT 与 KLT 之间必须通过**映射**搭桥：一个用户线程想真正上 CPU，背后必须有一个内核级执行流替它进内核、参与内核调度。三种模型就是"ULT 怎么依托 KLT"的三种方案。

#### 模型① 多对一：多个 ULT 挤一个 KLT

- **What**：n 个用户级线程映射到 **1 个**内核级线程；线程的建、销、切全部在用户空间**线程库**里完成，内核眼中的进程只有**一个**执行流。
- **Why**：历史产物——早期内核只支持传统进程、没有线程概念，线程库在用户态"模拟"出线程，内核**零改动**。
- **Where/Who**：管理全在用户层（线程库）；内核完全不参与线程管理。
- **Cost/Effect**：
  - 优点：线程切换不进内核、无模式切换，**开销最小**；线程数量不受内核资源限制（库想建多少建多少）。
  - 缺点：一个线程发起阻塞式系统调用 → **整个进程一起阻塞**（内核只看得到进程）；**无法利用多核**——内核只调度一条执行流，再多 ULT 也只能串行。
- 典型：不支持线程的老式内核上的线程库（早期 Java 绿色线程）。

#### 模型② 一对一：每个 ULT 配一个 KLT

- **What**：每创建一个用户线程，内核就同步创建一个内核级线程与之绑定（TCB 建在内核里），用户线程数 = 内核线程数。
- **Why**：根治多对一两大缺陷——线程阻塞只阻塞自己；KLT 可分散到多个 CPU **真并行**。
- **Where/Who**：线程由**内核管理**，创建、调度、切换都要经系统调用进内核。
- **Cost/Effect**：
  - 优点：一个线程阻塞不影响同进程其他线程；并发度最高、能用满多核。
  - 缺点：创建/切换都要进内核，**开销大**；每条 KLT 都要占内核的 TCB、栈等资源，**线程总数受内核限制**，不能无限建。
- 典型：现代主流系统——**Linux（pthread/NPTL）、Windows 均采用一对一**。

#### 模型③ 多对多：n 个 ULT 复用 m 个 KLT（n ≥ m）

- **What**：多个用户线程动态**复用**较少的内核线程；以内核提供的**轻量级进程 LWP** 作中间层，ULT 通过 LWP 搭到 KLT 上。部分 ULT 可绑定到固定 KLT，其余动态复用——故又称**两级线程模型（two-level）**。
- **Why**：折中——兼取多对一"切换快、省内核资源"与一对一"可并行、阻塞不连坐"两头优点：KLT 只需 m 个（m < n），并发线程不必一对一地消耗内核资源。
- **Where/Who**：用户库 + 内核**协同管理**：库管 ULT 到 LWP 的复用策略，内核管 KLT 调度。
- **Cost/Effect**：
  - 优点：兼顾切换效率与多核利用；线程数上限介于两者之间。
  - 缺点：实现**最复杂**——两级调度要协调，库与内核耦合深；纯多对多系统很少（经典实现如早期 Solaris）。
- 考研定位：记住"LWP 中间层 + 两级模型 + 折中"三个关键词即可，大题几乎不直接考实现细节。

#### 三模型对比（选择高频）

| 维度 | 多对一 | 一对一 | 多对多 |
|---|---|---|---|
| 内核可见的执行流数 | 1 | = ULT 数 | m 个（1 < m < n） |
| 一线程阻塞的影响 | **一阻全阻** | 只阻自己 | 只阻自己（该 ULT 搭上 KLT 时） |
| 多核并行 | 不能 | **能** | 能（搭上 KLT 的部分） |
| 线程切换开销 | 最小（纯用户态） | 最大（进内核） | 折中 |
| 线程数量上限 | 无内核限制 | 受内核资源限制 | 介于两者之间 |
| 典型系统 | 早期 Java 绿色线程 | **Linux / Windows** | 早期 Solaris（两级） |

> 记法：多对一"省内核但一损俱损"；一对一"能并行但费内核"；多对多"两头讨好但实现最难"。考试给一段系统描述，先数"内核看得见几条执行流"再对号入座。

### 进程 vs 线程（选择高频）

| 维度 | 进程 | 线程 |
|---|---|---|
| 资源 | 资源分配的基本单位，拥有独立地址空间 | 几乎不拥有资源，仅有运行必需的私有部分 |
| 调度 | 未引入线程时是调度单位 | 引入线程后是**调度基本单位**；同进程线程切换不引起进程切换 |
| 地址空间 | 进程间相互独立 | 同进程线程共享同一地址空间 |
| 开销 | 创建/撤销/切换大（切换要换页表、TLB 失效） | 都小，同进程切换不切地址空间 |
| 通信 | 必须用 IPC 三方式 | 直接读写共享变量（但仍需同步互斥） |

## 7. 处理机调度层次与调度准则

### 三级调度

| 级别 | 别名 | 做什么 | 频率 |
|---|---|---|---|
| 高级调度 | 作业调度 / 长程调度 | 从外存**后备队列**选作业调入内存、创建进程，放入就绪队列 | 最低，决定**多道程序度** |
| 中级调度 | 内存调度 / 中程调度 | 挂起进程与内存之间的**对换**（接 §3 七态） | 中等，调节内存负载 |
| 低级调度 | 进程调度 / 短程调度 | 从**就绪队列**选一个进程分配CPU（内存到CPU） | 最高，几十毫秒一次 |

一个作业的完整路径：**高级调度**选中入内存 → 在就绪队列里等 **低级调度**分 CPU → 内存紧张时由**中级调度**换进换出。

调度方式：

- **非抢占式**：CPU 一旦分配就一直运行到**终止或主动阻塞**才让出。实现简单、开销小，但紧急任务无法插队，适合批处理。
- **抢占式**：可依据**优先权、短作业、时间片原则**剥夺当前进程 CPU。响应及时、适合分时/实时，但切换开销大。

不能进行进程调度的场合（选择题）：**中断处理过程中**、进程处于**内核程序临界区**（独占内核数据结构时）、执行**原语（原子操作）**期间。

### 调度的四大评价指标（03 篇直接套用）

| 指标 | 定义/公式 | 说明 |
|---|---|---|
| CPU 利用率 | 忙碌时间 / 总时间 | 越高越好 |
| 吞吐量 | 单位时间内完成的作业数 | 批处理看重 |
| **周转时间** | T = 完成时刻 − 提交时刻 | 含**运行 + 就绪等待 + I/O 阻塞**全过程 |
| **带权周转时间** | W = T / 实际运行时间，W ≥ 1 | 越接近 1 越满意；先对每个作业算再平均 |
| 等待时间 | 进程在**就绪队列**中等待 CPU 的时间之和 | 注意口径：阻塞等 I/O 不计入等待时间 |
| **响应时间** | 提交请求 → **首次**响应的时间 | 交互式/分时系统第一目标 |

> 不同系统的目标不同：批处理重周转/吞吐/CPU 利用率；分时重响应时间与公平；实时重截止时间保证。这些目标互相矛盾，不存在对所有指标都最优的算法——所以 03 篇才要分算法讨论。

## 8. 典型题型与方法

**题型① 状态转换判定**：给一个事件写状态变化。
步骤：定位当前态 → 判主动还是被动（自己等事件 = 运行→阻塞；事件发生 = 阻塞→就绪；时间片/被抢 = 运行→就绪）。

| 事件 | 转换 |
|---|---|
| 进程执行 `read()` 等磁盘 | 运行 → 阻塞 |
| 磁盘 I/O 完成中断 | 阻塞 → 就绪（中断处理里调用 wakeup） |
| 时间片用完 | 运行 → 就绪 |
| 抢占式系统中更高优先级进程到达 | 当前进程 运行 → 就绪；新进程 就绪 → 运行 |
| 进程收到终止信号 | 运行 → 终止 |

**题型② 上下文切换次数计数**：n 个进程依次执行、中途不发生调度，进程切换次数 = **n − 1**（不含系统启动时的初始分派；若题目把首次分派也计数按其口径 +1）。

**题型③ 判断共享/私有**：看变量落在哪个区——全局/静态变量、malloc 出来的堆对象、文件描述符 = 线程共享；函数内局部变量和参数在栈上 = 线程私有。

**题型④ 指标定义小算**（完整算法题在 03 篇）：作业 0 时刻提交，CPU 运行共 4 个单位时间、其间 I/O 阻塞 2 个单位时间，6 时刻完成，全程无排队。
周转时间 = 6 − 0 = **6**；带权周转 = 6 / 4 = **1.5**。
要点：周转时间把 I/O 阻塞也算进去，而带权周转的分母只是纯运行时间，所以即便没排队 W 也可能 >1。

## 9. 易错点

- "PCB 是属于程序的数据结构"：错，PCB 属于**进程**，是进程存在的唯一标志。
- "阻塞进程等的事件到了就直接运行"：错，只能 **阻塞→就绪→运行**，必须再经调度。
- "唤醒由阻塞进程自己完成"：错，阻塞时它已不执行代码；wakeup 由其他进程或 OS 在中断处理中执行，与 block **成对出现**。
- "挂起就是阻塞"：错，阻塞的映像**在内存**里等事件；挂起是被换到**外存**，由中级调度管。
- "用户级线程里一个线程阻塞不影响别的线程"：错，内核看不见 ULT，一个阻塞式调用会让**整个进程**一起阻塞。
- "所有线程切换都要进内核"：错，用户级线程的切换在线程库完成，不进内核。
- "一对一模型想建多少线程就建多少"：错，每条 KLT 都占内核 TCB、栈等资源，线程总数受内核限制；不受内核限制的是**多对一**（库在用户态随意建）。
- "多对多模型的内核线程数 = 用户线程数"：错，多对多是 n ≥ m 的**复用**关系，内核线程数 m 介于 1 与 n 之间；执行流数 = ULT 数的是**一对一**。
- "进程是 CPU 调度的基本单位"：引入线程后调度单位是**线程**，进程只是资源分配单位。
- "模式切换就是进程切换"：错，每次系统调用/中断都有模式切换，但未必换进程。
- "周转时间只算等 CPU 的时间"：错，周转 = 完成 − 提交，运行、就绪等待、I/O 阻塞全包含；"等待时间"这个指标才只算就绪队列等 CPU 的部分，审题先分清问哪个。
- "中级调度就是进程调度"：错，中级管内外存对换，低级（进程调度）才管 CPU 分派。
- "作业就是进程"：错，作业是批处理提交单位，被高级调度选中后才创建为一个或多个进程。
