02 篇给过结论：同进程的多个线程**共享堆、全局变量和打开的文件**。共享就会打架。

一条 `count++` 在机器层面是三条指令：`load → add → store`。两个线程各对 count 执行 1000 次自增，结果可能**小于 2000**：

```text
初始 count = 0
线程A: load(0) ──被打断──→ add1 ──→ store(1)
线程B:            load(0) → add1 → store(1)
两次自增，只加了 1
```

这种"多个进程/线程因共享变量的访问次序不同而结果不同"的现象叫**竞态条件（Race Condition）**。本篇全部内容就是回答：怎样让并发执行的结果**确定且正确**。

## 2. 基本概念

| 概念 | 定义 |
|---|---|
| **临界资源**【必背】 | 一段时间内**只允许一个**进程（线程）访问的共享资源，如共享变量、打印机、共享缓冲区 |
| **临界区**【必背】 | 进程中**访问临界资源的那段代码**。进程进入临界区前要加检查，退出后要释放 |
| **互斥**（间接制约） | 多个进程争用同一临界资源：你用我等，也称间接相互制约 |
| **同步**（直接制约） | 协作进程间需要按**约定次序**执行：你先走我再走，也称直接相互制约 |

临界区在代码中的四段结构：

```text
进入区 entry ：检查能否进入，能则加锁（设标志/semwait 操作）
临界区 CS    ：访问临界资源的代码
退出区 exit  ：解锁（清标志/semsignal 操作）
剩余区       ：其余代码
```

> 互斥问"能不能同时进"；同步问"谁必须先完成"。一个信号量可以同时承担两种角色（见生产者-消费者的 mutex 与 empty/full）。

## 3. 临界区访问的四准则

1. **空闲让进**：临界区空闲时，应允许一个请求进入的进程立即进入；
2. **忙则等待**：已有进程在临界区内时，其他请求者必须等待；
3. **有限等待**：请求者应在**有限时间内**进入，不能无限期饿死；
4. **让权等待**：不能进入时应**立即释放 CPU**（阻塞），不能忙等着白占 CPU。

> 记法："**空闲让进、忙则等待、有限等待、让权等待**"。前三条管正确性，第四条管效率，后面所有实现方法的缺陷，都能归入"违反了第几条"。

> **"违反哪条准则"判断**：给一种实现（单标志/双标志/Peterson/关中断/TS/Swap）问缺陷，拿四准则逐条对照，先分清是正确性问题（忙则等待、空闲让进、有限等待）还是效率问题（让权等待）。

## 4. 早期实现：软件四法与硬件指令（只考结论）

### 4.1 软件方法（两个进程，标志位怎么摆）

| 方法 | 核心机制 | 缺陷（对应准则） |
|---|---|---|
| 单标志法 | 一个 `turn` 变量指定该谁进 | 必须**轮流**进入；对方不进，自己再闲也不能进 → 违反**空闲让进**；等不到时还忙等 → 违反**让权等待** |
| 双标志先检查法 | 各自有 `flag[]`，**先检查对方再置自己的标志** | "检查"和"上锁"不是原子的，两进程可同时检查通过、**同时进入** → 违反**忙则等待** |
| 双标志后检查法 | **先置自己的标志再检查对方** | 两进程可能同时置位、互相等待，**谁也进不去** → 违反**空闲让进、有限等待** |
| Peterson 算法 | 双标志 + 谦让变量 `turn`：想进先举手，再把进入权让给对方 | 前三条都满足；仍是 `while` 自旋 → **不满足让权等待** |

> 选择题套路：题目描述"轮流、谦让"想单标志/Peterson；描述"两个标志、检查与置位先后"想两种双标志法。

### 4.2 硬件方法

| 方法 | 机制 | 适用与缺陷 |
|---|---|---|
| 关中断 | 进入临界区关中断，退出开中断 | 简单高效；**只适用单处理机内核**（多处理机上别的核照跑），用户态无权关中断；临界区长会影响系统响应 |
| TestAndSet（TS/TSL 指令） | 一条原子指令完成"读出旧值并置真" | 适用多处理机；满足前三条；得不到锁就**自旋** → 违反让权等待，且可能饥饿 |
| Swap（XCHG）指令 | 原子交换两个变量内容 | 结论与 TS 完全相同：忙则等待有了，让权等待没有 |

软件四法和 TS/Swap 的共同短板都是**忙等**。要满足让权等待，需要一种"等不到就阻塞、semsignal 时再唤醒"的机制，信号量。

## 5. 信号量机制

### 5.1 从整型到记录型

- **整型信号量**：`wait(S){ while(S≤0); S--; }`、`signal(S){ S++; }`。semwait 操作等不到时**循环空转**，未满足让权等待。
- **记录型信号量**【主体】：信号量 = 一个整型 value + 一个等待队列 L：

```c
typedef struct {
    int value;              // 资源计数
    struct process *L;      // 等待队列
} semaphore;

semwait(S):  S.value--;
      if (S.value < 0)  block(S.L);   // 自我阻塞，挂到 S 的等待队列

semsignal(S):  S.value++;
      if (S.value <= 0) wakeup(S.L);  // 从队列唤醒一个
```

semwait、semsignal 都是**原语**，不可中断。value的读法【必背】：

| value 的值 | 含义 |
|---|---|
| > 0 | 当前**可用资源数** |
| = 0 | 资源恰好用完，且无人等待 |
| < 0 | 资源用完且有进程等待，**绝对值 = 等待队列中的进程数** |

- semwait 是"先减后判"：减完仍 ≥0 说明拿到资源，**不阻塞**；
- semsignal 是"先加后判"：加完仍 ≤0 说明队列里还有人，**唤醒一个**；
- semsignal 必须有对应的 semwait，但 semsignal 一个**至多唤醒一个**进程。

> **value 判读**：给一段连续 semwait/semsignal 序列，问 value 值与阻塞进程数——按执行序列逐条模拟，只盯两件事：value 当前值、等待队列人数；value < 0 时 |value| = 队列长度。

### 5.2 三类信号量的初值

| 用途 | 初值 | 说明 |
|---|---|---|
| 互斥信号量 | **1** | 临界资源只有一份 |
| 同步信号量 | **0**（或初始可用资源数） | 表示"前序事件"尚未发生，发生后由前序方 semsignal |
| 资源信号量 | **n** | 有 n 份同类资源（如 n 个缓冲区、n 台打印机） |

## 6. PV 大题三步模板

```
第 1 步  数角色、列关系
         · 有哪几类进程？各自的动作序列是什么？
         · 同步关系（谁必须在谁之前）逐条列出
         · 临界资源逐个列出（共享缓冲区、共享变量、台子……）

第 2 步  设信号量
         · 每条同步关系设 1 个同步信号量，初值看初始状态（通常 0）
         · 每个临界资源设 1 个互斥信号量，初值 1
         · n 份同类资源设 1 个资源信号量，初值 n

第 3 步  写代码
         · 同步：前序操作之后 semsignal，后序操作之前 semwait（"前 semsignal 后 semwait"）
         · 互斥：进临界区 semwait，出临界区 semsignal
         · 铁律：同步 semwait 必须写在互斥 semwait 之前（semsignal 的顺序可互换）
```

**最简示例**：要求进程 A 的语句 `a1` 必须先于进程 B 的 `b1` 执行。
设同步信号量 `S = 0`：

```c
A: a1; semsignal(S);      // 前序完成，发信号
B: semwait(S); b1;      // 没等到就阻塞
```

同步关系从 1 条增加到多条，就是第 7 节的各经典模型。

> **semwait/semsignal 大题收尾必查两处**：同步 semwait 是否都写在互斥 semwait 之前；每个 semwait 是否都有配对的 semsignal。

## 7. 六个经典模型

### 7.1 生产者-消费者（环形缓冲区 n）

n 个槽位的缓冲池，生产者放产品、消费者取产品。不能放满、不能取空、存取操作互斥。

| 信号量 | 含义 | 初值 |
|---|---|---|
| `empty` | 空槽数（生产者的资源） | **n** |
| `full` | 满槽数（消费者的资源） | **0** |
| `mutex` | 对缓冲区操作互斥 | **1** |

```c
生产者:  semwait(empty);  semwait(mutex);  放入产品;  semsignal(mutex);  semsignal(full);
消费者:  semwait(full);   semwait(mutex);  取出产品;  semsignal(mutex);  semsignal(empty);
```

**最高频考点，semwait 的顺序不能反**：若生产者先 `semwait(mutex)` 再 `semwait(empty)`，缓冲区满时生产者持锁等空槽，而消费者拿不到锁取货 → 双方永久卡住（04 篇的死锁）。两个 **semsignal 的顺序可以互换**。

### 7.2 多生产者-多消费者（苹果橘子 / 放盘子）

父亲放苹果、母亲放橘子，儿子只吃橘子、女儿只吃苹果；桌上一次只能放一个水果。

| 信号量 | 含义 | 初值 |
|---|---|---|
| `plate` | 盘子（台子）容量 | **1** |
| `apple` / `orange` | 桌上有无对应水果 | **0 / 0** |

```c
父亲: semwait(plate); 放苹果;   semsignal(apple);
母亲: semwait(plate); 放橘子;   semsignal(orange);
儿子: semwait(orange); 取橘子;  semsignal(plate);
女儿: semwait(apple);  取苹果;  semsignal(plate);
```

要点：容量为 1 时 `plate` 兼任互斥（同一时刻最多一个水果，存取不会撞车），所以**没有单独的 mutex**；盘子容量 >1 时必须补互斥信号量。

### 7.3 吸烟者问题（一个供应者 + 三个取料者）

三种材料 A、B、C，三名吸烟者分别自带 A、B、C，缺另外两种；供应者每次随机往桌上放两种，恰好缺的人取走卷烟，抽完供应者再发下一轮。

```c
semaphore offer1=0, offer2=0, offer3=0;   // 三种组合各对应一人
semaphore finish = 0;                      // 吸烟者抽完的回执

供应者:  i = 随机数 % 3;
         i==0: 放B、C; semsignal(offer1);
         i==1: 放A、C; semsignal(offer2);
         i==2: 放A、B; semsignal(offer3);
         semwait(finish);                        // 等本轮抽完

吸烟者1(带A): semwait(offer1); 取料卷烟抽; semsignal(finish);
吸烟者2(带B): semwait(offer2); 取料卷烟抽; semsignal(finish);
吸烟者3(带C): semwait(offer3); 取料卷烟抽; semsignal(finish);
```

要点：本质是"**一个供应者对多个不同消费者**"，用多个 offer 信号量区分产品类型；`finish` 是容量同步信号量，保证一轮只发一次料。

### 7.4 读者-写者（读者优先）

一个共享文件：允许多个读者同时读；写者必须独占（写写互斥、读写互斥）。

```c
semaphore rw = 1;       // 写者与"第一个/最后一个读者"之间的锁
semaphore mutex = 1;    // 保护共享计数 count
int count = 0;          // 当前读者数

读者: semwait(mutex);
      if (count == 0) semwait(rw);   // 第一个读者锁门
      count++;
      semsignal(mutex);
      ────── 读文件 ──────
      semwait(mutex);
      count--;
      if (count == 0) semsignal(rw);   // 最后一个读者开门
      semsignal(mutex);

写者: semwait(rw);  ── 写文件 ──  semsignal(rw);
```

要点：① 读者**成群**进出，`rw` 由第一个读者 semwait、最后一个读者 semsignal；② `count` 是普通共享变量，自增自减要在 `mutex` 里，更关键的是"**判断 + 抢锁 + 改计数**"必须整体原子；③ 此版**读者优先**：只要还有读者到达，写者就一直等，可能**写者饥饿**；写者优先见 §7.5，读写公平见 §7.6。

**为什么 `if (count == 0) semwait(rw); count++;` 要整段包在 `mutex` 里**

`mutex` 保护的是"读 `count` → 判断是不是第一个/最后一个读者 → 据此 semwait/semsignal `rw` → 改 `count`"这一整段的**原子性**。`count++` 只是其中一步；真正危险的是**判断结果决定要不要碰 `rw`**——判断与它触发的锁操作必须和 `count` 的改动同时生效，否则 `count` 与 `rw` 的配对关系会错位。

| 环节 | 拆开原子性后的错误交错 | 后果 |
|---|---|---|
| 进入：判断 + `count++` 不是整体 | R2 读到 `count != 0`，判定"我不是第一个、不用碰 `rw`"；此时 R1 作为最后一个读者 `count-- → 0` 并 `semsignal(rw)`，写者拿到 `rw` 开始写；R2 这才 `count++` 进入读 | **写者与读者同时进入临界区**，读写互斥被破坏 |
| 退出：`count--` 与判 0 不是整体 | 两个读者几乎同时收尾，都读到 `count == 0`，于是各 `semsignal(rw)` 一次 | `rw` 从 1 被推到 2，写者能与读者同时进，互斥同样失效 |

两处错误的共同点是：**"我以为自己不是第一个/最后一个"这个判断，和 `count` 的最终值不一致**。只要判断和 `count` 改动之间存在窗口，读者就会基于过期信息决定是否操作 `rw`，把一个该加的锁漏掉，或把不该做的 `semsignal` 多做一次。

两个补充辨析：

- **只把 `semwait(rw)` 放进临界区、`count++` 却在临界区外**，同样不行——判断、抢锁、计数必须是一个不可分割的动作。教材里把它们写在同一个 `semwait(mutex)…semsignal(mutex)` 之间，就是这个原因。
- **"两个读者都判定自己是第一个、都去 `semwait(rw)`"** 这一情形，若 `rw` 是真正的记录型信号量，第二个 `semwait(rw)` 只会**阻塞排队**，本身不会破坏互斥，也不会死锁（前一个读者最终 `semsignal(rw)` 会唤醒它）；它真正的危害是让 `count` 与 `rw` 的持有关系脱节，一旦叠加退出段的判 0，就退化成上表第一行那种"写者与读者并发"。

记法：`mutex` 圈住的是**"`count` 的判定与使用"整个临界区**，不是单独一个 `count++`；判断与动作不原子，读者就会集体误判"我是第一个/最后一个读者"，把 `rw` 用错。

### 7.5 读者-写者（写者优先）

读者优先的毛病是**写者饥饿**：读者源源不断时，写者可能永远等不到 `rw`。写者优先在门口加一道"写者闸门"，只要写者在等，新读者就被拦在外面。

| 信号量/变量 | 含义 | 初值 |
|---|---|---|
| `rw` | 文件锁（写者 vs 全体读者） | **1** |
| `mutex` | 保护 `readcount` | **1** |
| `wmutex` | 保护 `writecount` | **1** |
| `readTry` | 写者闸门：第一个写者关上，最后一个写者打开 | **1** |
| `readcount` / `writecount` | 当前读者数 / 写者数 | **0 / 0** |

```c
读者: semwait(readTry);                 // 有写者在等就排队
      semwait(mutex);
      readcount++;
      if (readcount == 1) semwait(rw);  // 第一个读者锁文件
      semsignal(mutex);
      semsignal(readTry);                 // 登记完迅速放闸，其他读者可继续进
      ────── 读文件 ──────
      semwait(mutex);
      readcount--;
      if (readcount == 0) semsignal(rw);
      semsignal(mutex);

写者: semwait(wmutex);
      writecount++;
      if (writecount == 1) semwait(readTry);  // 第一个写者关上闸门，拦住后续读者
      semsignal(wmutex);
      semwait(rw);                            // 等现有读者全部退场
      ────── 写文件 ──────
      semsignal(rw);
      semwait(wmutex);
      writecount--;
      if (writecount == 0) semsignal(readTry);  // 最后一个写者开闸
      semsignal(wmutex);
```

要点：① 闸门 `readTry` 由**第一个写者 semwait、最后一个写者 semsignal**，作用是把"有写者在等"这件事通知读者；② 写者之间靠 `rw` 与 `writecount` 排队：第二个及以后的写者不再碰 `readTry`，直接卡在 `rw` 上；③ 代价是**读者可能饥饿**，写者不断到来时读者一直被闸门拦着——这正是读者优先的对偶。

### 7.6 读者-写者（读写公平）

公平版的目标是"先来先服务"：读者和写者按到达顺序排队，谁也饿不死。做法是在门外加一个**排队信号量 `w`**，两类角色进门都先 semwait(w)，读者登记完立刻放行下一位，写者则一直占到写完。

```c
semaphore rw = 1;      // 文件锁
semaphore mutex = 1;   // 保护 readcount
semaphore w = 1;       // 排队闸门：先到先得
int readcount = 0;

读者: semwait(w);                        // 排队进门
      semwait(mutex);
      readcount++;
      if (readcount == 1) semwait(rw);   // 第一个读者锁文件
      semsignal(mutex);
      semsignal(w);                        // 只占登记这一小段，立刻放行下一位
      ────── 读文件 ──────
      semwait(mutex);
      readcount--;
      if (readcount == 0) semsignal(rw);
      semsignal(mutex);

写者: semwait(w);                        // 排队进门，并且一直占到写完
      semwait(rw);
      ────── 写文件 ──────
      semsignal(rw);
      semsignal(w);
```

要点：① 关键差别是**谁占着 `w` 不撒手**：读者只占"登记 readcount"这一小段，写者占整个写过程，于是写者排队时，后来到达的读者只能排在它后面；② `w` 的等待队列近似 FIFO，先到者先获得，读者、写者都不能被对方无限插队——这就是"公平"；③ 比写者优先少一个 `writecount`/`wmutex`，代价是严格依赖信号量队列的 FIFO 语义，部分教材称"读写公平 / 先来先服务"版。

三种政策放在一起对比：

| 版本 | 信号量 | 优先对象 | 饥饿风险 |
|---|---|---|---|
| 读者优先（§7.4） | `rw`、`mutex` | 读者 | 写者可能饥饿 |
| 写者优先（§7.5） | `rw`、`mutex`、`wmutex`、`readTry` | 写者 | 读者可能饥饿 |
| 读写公平（§7.6） | `rw`、`mutex`、`w` | 先到者 | 无（依赖 FIFO） |

### 7.7 哲学家进餐（防死锁专题）

5 位哲学家围坐，两人间一支筷子共 5 支，必须拿到左右两支才能吃。朴素写法：

```c
semaphore chop[5] = {1,1,1,1,1};
第 i 位: semwait(chop[i]);  semwait(chop[(i+1)%5]);  吃饭;  semsignal(chop[(i+1)%5]);  semsignal(chop[i]);
```

所有人同时拿起左筷 → 每个人都等右筷 → **循环等待，全部死锁**（04 篇死锁四条件的现实版本）。三种标准防法：

| 防法 | 做法 | 破坏的条件（04 篇详讲） |
|---|---|---|
| 限制人数 | 加 `room = 4`，拿筷前先 semwait(room) | 循环等待（至少一人能拿到两支） |
| 奇偶错峰 | 奇数号先左后右，偶数号先右后左 | 循环等待 |
| 同时拿两支 | 左右都可用才用原子操作一次拿走（AND 信号量/管程封装） | 占有并等待 |

### 7.8 睡眠理发师（1 理发师 + N 等候椅）

理发店有 1 位理发师、1 把理发椅、N 把等候椅。没有顾客时理发师在理发椅上睡觉；顾客到来时：理发师睡则叫醒他，理发师忙且有空椅则坐下等待，等候椅全满则直接离开。1965 年由 Dijkstra 提出（EWD-123《Co-operating Sequential Processes》），是经典的"有限容量 + 双向会合"模型。

| 信号量/变量 | 含义 | 初值 |
|---|---|---|
| `customers` | 等待理发的顾客数（**不含**正在理发者），理发师在此上等顾客 | **0** |
| `barbers` | 正在等待顾客的理发师数（0 或 1），顾客在此上等理发师就绪 | **0** |
| `mutex` | 保护 waiting 计数器的互斥锁 | **1** |
| `waiting` | 等候区人数（普通整型变量，不是信号量） | **0** |

```c
理发师: while (TRUE) {
          semwait(customers);   // 无顾客则阻塞——睡觉
          semwait(mutex);
          waiting--;      // 顾客进入理发椅，等候区人数减 1
          semsignal(barbers);     // 通知顾客：理发师已就绪
          semsignal(mutex);
          cut_hair();     // 理发在临界区外进行
        }

顾客:   semwait(mutex);
        if (waiting < CHAIRS) {   // 等候区有空位
          waiting++;
          semsignal(customers);          // 通知理发师有顾客
          semsignal(mutex);              // 先释放锁……
          semwait(barbers);            // ……再等理发师就绪
          get_haircut();
        } else {
          semsignal(mutex);              // 等候区已满，直接离开
        }
```

要点：① **waiting 必须是普通变量而非信号量**：信号量当前值不可读，顾客无从判断"是否已满"；② 两个同步信号量构成**双向会合**：顾客 semsignal(customers) 唤醒理发师，理发师 semsignal(barbers) 放行顾客；③ 顾客必须**先 semsignal(mutex) 再 semwait(barbers)**：持锁等理发师，而理发师拿不到 mutex 就无法 semsignal(barbers)，立即死锁；④ 此解法无死锁，但不保证 FIFO，可能顾客饥饿，改用严格队列可解决。

> **死锁预判**：给 semwait/semsignal 写法问"会不会永久等待"——找"semwait 在等的资源被另一个也在等的进程握着"的环路，生产者-消费者反序 semwait、哲学家朴素解、理发师持 mutex 等 barbers 都是标本；系统化判定（四条件、资源分配图）在 04 篇。

## 8. 管程

信号量的 semwait/semsignal 分散写在每个进程里，顺序错了就死锁。管程把同步逻辑**集中封装**：

- **组成**：管程名称 + 共享数据结构 + 对数据操作的一组过程（方法）+ 初始化语句。
- **核心特性**：**任一时刻最多一个进程在管程内执行方法**：互斥由编译器/语言运行时保证，程序员不再手写 semwait/semsignal。
- **条件变量** `condition x`：管程内资源暂不满足时用两个操作协调：
  - `x.wait()`：阻塞并**让出管程**，挂到 x 的等待队列；
  - `x.signal()`：唤醒 x 队列中一个进程；**若队列空，signal 什么也不发生（信号不累积）**。

`x.signal()` 与信号量 `semsignal`【辨析】：

| | 管程 `x.signal()` | 信号量 `semsignal` |
|---|---|---|
| 空队列 | **空操作**，状态不变 | **总会** `s.value++`，信号可累积 |
| 执行后 | 立即**退出管程**（互斥交给被唤醒者或下一位） | 可能继续跑，也可能自己被阻塞 |

条件变量 vs 信号量：wait/signal 与 semwait/semsignal 都能阻塞、唤醒。信号量自带整数值，反映可用资源数；条件变量**不维护数值**，只排队和通知。管程里资源数量由共享变量（如 `count`/`S`）显式记录，条件变量只负责同步。

| 对比项 | 信号量 | 管程 |
|---|---|---|
| 互斥谁保证 | 程序员自己写 semwait/semsignal | 编译器保证，每次只进一个 |
| wait/queue | semwait/semsignal 合一：计数 + 队列 | 条件变量只排队、**不计数**，空 signal 无效；资源数在共享变量上 |
| 出错面 | semwait/semsignal 分散，顺序错会死锁 | 同步集中在方法内，不易错 |
| 典型语言 | 一切系统 | Java `synchronized`/`wait/notify`、Hoare 管程、Python Condition |

## 9. 模型识别卡（看到题干词 → 套模型）

| 题干特征 | 模型 | 信号量骨架 |
|---|---|---|
| 缓冲区有 n 个位置，放/取两类角色 | 生产者-消费者 | empty=n, full=0, mutex=1 |
| 一个台子放一种特定产品，多个角色各取所需 | 苹果橘子 | plate=1 + 每种产品一个 0 信号量 |
| 一个供应者发不同组合，多个不同等待者 | 吸烟者 | 每消费者一个 offer + 一个 finish |
| "多个人可以同时读，写要独占" | 读者-写者 | rw=1 + 保护 count 的 mutex=1 |
| "写者不能被读者饿死" | 读者-写者（写者优先） | 再加 wmutex=1 + readTry=1 + writecount |
| "读者写者先来先服务" | 读者-写者（读写公平） | 再加排队闸门 w=1 |
| 环形资源、每人要拿左右两个 | 哲学家进餐 | 必写防死锁三法之一 |
| 一个服务者 + 有限等候位，无客则睡、满了则走 | 睡眠理发师 | customers=0, barbers=0, mutex=1, waiting=0 |
| 只要求"A 的某步在 B 某步之前" | 纯同步 | 一个初值 0 的信号量，前 semsignal 后 semwait |

> 先认模型再动笔，模型认错全盘皆错；认不准时数"几类角色 + 几个临界资源 + 几条先后关系"。

## 10. 最容易写错的十六处（速查清单）

1. **互斥 semwait 写在同步 semwait 前面**：生产者-消费者头号死锁写法；记"先看有没有资源，再去抢锁"；semsignal 顺序无所谓。
2. "semwait 操作一定会阻塞"：错，semwait 先 value--，减完仍 ≥0 就直接通过；阻塞条件是减完 <0。
3. "信号量初值可以设成负数"：错，初值只能 ≥0；负值只在运行中出现，其绝对值是等待进程数。
4. "semsignal 操作会让信号量一直积累信号"：记录型 semsignal 只唤醒队列；管程 signal 对空队列完全无效，两者别混。
5. "读者-写者只需一个 rw 信号量"：漏了保护 count 的 mutex。它护的不只是 count++，而是"判断 count==0 + 据此 semwait(rw) + 改 count"整段原子；判断与改动不原子，读者会误判自己是不是第一个/最后一个，导致该加的锁漏加、该 semsignal 的锁多 semsignal。
6. "读者越多越乱"：错，读读不互斥，这是允许读者并发的原因；乱在 count 的判定与修改没有整体原子，不在读文件本身。
7. 双标志先检查违反"忙则等待"（同时进）；后检查违反"空闲让进/有限等待"（都进不去）；Peterson 违反"让权等待"（自旋）。
8. "关中断能在多核上互斥"：错，只对单处理机有效；TSL/Swap 才支持多处理机，但都是忙等。
9. 苹果橘子题中 plate=1 已隐含互斥，再叠 mutex 是误写（容量 >1 才必须加）。
10. 哲学家题只写朴素拿筷不写防死锁措施等于没答完，必须给三法之一并指明破坏的条件。
11. 理发师题中顾客持 mutex 等 semwait(barbers) 是死锁写法，必须先 semsignal(mutex) 再 semwait(barbers)；waiting 要设成普通变量。
12. PV 是原语、不可中断；但用户态调用 semwait/semsignal 会经内核态阻塞/唤醒，"不可中断"指原语原子性，不是说进程不会阻塞。
13. "整型和记录型的 semwait 是同一种写法"：错，整型先判后减（忙等），记录型先减后判（<0 才阻塞入队）；混出时先认哪种。
14. 把管程 `signal` 写成 semsignal：空队列时 signal 是空操作，semsignal 总会 `value++`；signal 后立即出管程，`semsignal` 后可能继续跑。条件变量不计数，资源数记在管程共享变量上。
15. 写者优先版里 `readTry` 的 semwait/semsignal 挂错人：它由**第一个写者 semwait、最后一个写者 semsignal**，且受 `writecount` 双计数控制；写成每个写者都 semwait/semsignal，闸门就失去"只要有写者在等就拦住新读者"的作用。
16. 公平版里读者占着 `w` 不放：读者必须在登记完 `readcount` 后**立即 semsignal(w)**，否则一个读者就把整扇门焊死，退化成读者串行、写者更进不来。写者才全程持有 `w`。
