一条 `count++` 在机器层面是三条指令：`load → add → store`。两个线程各对 count 执行 1000 次自增，结果可能**小于 2000**：

```text
初始 count = 0
线程A: load(0) ──被打断──→ add1 ──→ store(1)
线程B:            load(0) → add1 → store(1)
两次自增，只加了 1
```

这种"多个进程/线程因共享变量的访问次序不同而结果不同"的现象叫**竞态条件（Race Condition）**。本篇全部内容就是回答：怎样让并发执行的结果**确定且正确**。

## 2. 基本概念

| 概念 | 定义 |
|---|---|
| **临界资源**【必背】 | 一段时间内**只允许一个**进程（线程）访问的共享资源，如共享变量、打印机、共享缓冲区 |
| **临界区**【必背】 | 进程中**访问临界资源的那段代码**。进程进入临界区前要加检查，退出后要释放 |
| **互斥**（间接制约） | 多个进程争用同一临界资源：你用我等，也称间接相互制约 |
| **同步**（直接制约） | 协作进程间需要按**约定次序**执行：你先走我再走，也称直接相互制约 |

临界区在代码中的四段结构：

```text
进入区 entry ：检查能否进入，能则加锁（设标志/P操作）
临界区 CS    ：访问临界资源的代码
退出区 exit  ：解锁（清标志/V操作）
剩余区       ：其余代码
```

> 互斥问"能不能同时进"；同步问"谁必须先完成"。一个信号量可以同时承担两种角色（见生产者-消费者的 mutex 与 empty/full）。

## 3. 临界区访问的四准则【必背】

1. **空闲让进**：临界区空闲时，应允许一个请求进入的进程立即进入；
2. **忙则等待**：已有进程在临界区内时，其他请求者必须等待；
3. **有限等待**：请求者应在**有限时间内**进入，不能无限期饿死；
4. **让权等待**：不能进入时应**立即释放 CPU**（阻塞），不能忙等着白占 CPU。

> 记法："**空闲让进、忙则等待、有限等待、让权等待**"。前三条管正确性，第四条管效率——后面所有实现方法的缺陷，都能归入"违反了第几条"。

## 4. 早期实现：软件四法与硬件指令（只考结论）

### 4.1 软件方法（两个进程，标志位怎么摆）

| 方法 | 核心机制 | 缺陷（对应准则） |
|---|---|---|
| 单标志法 | 一个 `turn` 变量指定该谁进 | 必须**轮流**进入；对方不进，自己再闲也不能进 → 违反**空闲让进**；等不到时还忙等 → 违反**让权等待** |
| 双标志先检查法 | 各自有 `flag[]`，**先检查对方再置自己的标志** | "检查"和"上锁"不是原子的，两进程可同时检查通过、**同时进入** → 违反**忙则等待** |
| 双标志后检查法 | **先置自己的标志再检查对方** | 两进程可能同时置位、互相等待，**谁也进不去** → 违反**空闲让进、有限等待** |
| Peterson 算法 | 双标志 + 谦让变量 `turn`：想进先举手，再把进入权让给对方 | 前三条都满足；仍是 `while` 自旋 → **不满足让权等待** |

> 选择题套路：题目描述"轮流、谦让"想单标志/Peterson；描述"两个标志、检查与置位先后"想两种双标志法。

### 4.2 硬件方法

| 方法 | 机制 | 适用与缺陷 |
|---|---|---|
| 关中断 | 进入临界区关中断，退出开中断 | 简单高效；**只适用单处理机内核**（多处理机上别的核照跑），用户态无权关中断；临界区长会影响系统响应 |
| TestAndSet（TS/TSL 指令） | 一条原子指令完成"读出旧值并置真" | 适用多处理机；满足前三条；得不到锁就**自旋** → 违反让权等待，且可能饥饿 |
| Swap（XCHG）指令 | 原子交换两个变量内容 | 结论与 TS 完全相同：忙则等待有了，让权等待没有 |

软件四法和 TS/Swap 的共同短板都是**忙等**。要满足让权等待，需要一种"等不到就阻塞、V 时再唤醒"的机制——信号量。

## 5. 信号量机制

### 5.1 从整型到记录型

- **整型信号量**：`wait(S){ while(S≤0); S--; }`、`signal(S){ S++; }`。P 操作等不到时**循环空转**，未满足让权等待。
- **记录型信号量**【主体】：信号量 = 一个整型 value + 一个等待队列 L：

```c
typedef struct {
    int value;              // 资源计数
    struct process *L;      // 等待队列
} semaphore;

P(S):  S.value--;
      if (S.value < 0)  block(S.L);   // 自我阻塞，挂到 S 的等待队列

V(S):  S.value++;
      if (S.value <= 0) wakeup(S.L);  // 从队列唤醒一个
```

P、V 都是**原语**，不可中断。value 的读法【必背】（选择/大题都考）：

| value 的值 | 含义 |
|---|---|
| > 0 | 当前**可用资源数** |
| = 0 | 资源恰好用完，且无人等待 |
| < 0 | 资源用完且有进程等待，**绝对值 = 等待队列中的进程数** |

- P 是"先减后判"：减完仍 ≥0 说明拿到资源，**不阻塞**；
- V 是"先加后判"：加完仍 ≤0 说明队列里还有人，**唤醒一个**；
- V 必须有对应的 P，但 V 一个**至多唤醒一个**进程。

### 5.2 三类信号量的初值

| 用途 | 初值 | 说明 |
|---|---|---|
| 互斥信号量 | **1** | 临界资源只有一份 |
| 同步信号量 | **0**（或初始可用资源数） | 表示"前序事件"尚未发生，发生后由前序方 V |
| 资源信号量 | **n** | 有 n 份同类资源（如 n 个缓冲区、n 台打印机） |

## 6. PV 大题三步模板

```
第 1 步  数角色、列关系
         · 有哪几类进程？各自的动作序列是什么？
         · 同步关系（谁必须在谁之前）逐条列出
         · 临界资源逐个列出（共享缓冲区、共享变量、台子……）

第 2 步  设信号量
         · 每条同步关系设 1 个同步信号量，初值看初始状态（通常 0）
         · 每个临界资源设 1 个互斥信号量，初值 1
         · n 份同类资源设 1 个资源信号量，初值 n

第 3 步  写代码
         · 同步：前序操作之后 V，后序操作之前 P（"前 V 后 P"）
         · 互斥：进临界区 P，出临界区 V
         · 铁律：同步 P 必须写在互斥 P 之前（V 的顺序可互换）
```

**最简示例**：要求进程 A 的语句 `a1` 必须先于进程 B 的 `b1` 执行。
设同步信号量 `S = 0`：

```c
A: a1; V(S);      // 前序完成，发信号
B: P(S); b1;      // 没等到就阻塞
```

同步关系从 1 条增加到多条，就是第 7 节的各经典模型。

## 7. 五个经典模型

### 7.1 生产者-消费者（环形缓冲区 n）

n 个槽位的缓冲池，生产者放产品、消费者取产品。不能放满、不能取空、存取操作互斥。

| 信号量 | 含义 | 初值 |
|---|---|---|
| `empty` | 空槽数（生产者的资源） | **n** |
| `full` | 满槽数（消费者的资源） | **0** |
| `mutex` | 对缓冲区操作互斥 | **1** |

```c
生产者:  P(empty);  P(mutex);  放入产品;  V(mutex);  V(full);
消费者:  P(full);   P(mutex);  取出产品;  V(mutex);  V(empty);
```

**最高频考点——P 的顺序不能反**：若生产者先 `P(mutex)` 再 `P(empty)`，缓冲区满时生产者持锁等空槽，而消费者拿不到锁取货 → 双方永久卡住（03 篇的死锁）。两个 **V 的顺序可以互换**。

### 7.2 多生产者-多消费者（苹果橘子 / 放盘子）

父亲放苹果、母亲放橘子，儿子只吃橘子、女儿只吃苹果；桌上一次只能放一个水果。

| 信号量 | 含义 | 初值 |
|---|---|---|
| `plate` | 盘子（台子）容量 | **1** |
| `apple` / `orange` | 桌上有无对应水果 | **0 / 0** |

```c
父亲: P(plate); 放苹果;   V(apple);
母亲: P(plate); 放橘子;   V(orange);
儿子: P(orange); 取橘子;  V(plate);
女儿: P(apple);  取苹果;  V(plate);
```

要点：容量为 1 时 `plate` 兼任互斥（同一时刻最多一个水果，存取不会撞车），所以**没有单独的 mutex**；盘子容量 >1 时必须补互斥信号量。

### 7.3 吸烟者问题（一个供应者 + 三个取料者）

三种材料 A、B、C，三名吸烟者分别自带 A、B、C，缺另外两种；供应者每次随机往桌上放两种，恰好缺的人取走卷烟，抽完供应者再发下一轮。

```c
semaphore offer1=0, offer2=0, offer3=0;   // 三种组合各对应一人
semaphore finish = 0;                      // 吸烟者抽完的回执

供应者:  i = 随机数 % 3;
         i==0: 放B、C; V(offer1);
         i==1: 放A、C; V(offer2);
         i==2: 放A、B; V(offer3);
         P(finish);                        // 等本轮抽完

吸烟者1(带A): P(offer1); 取料卷烟抽; V(finish);
吸烟者2(带B): P(offer2); 取料卷烟抽; V(finish);
吸烟者3(带C): P(offer3); 取料卷烟抽; V(finish);
```

要点：本质是"**一个供应者对多个不同消费者**"，用多个 offer 信号量区分产品类型；`finish` 是容量同步信号量，保证一轮只发一次料。

### 7.4 读者-写者（读者优先）

一个共享文件：允许多个读者同时读；写者必须独占（写写互斥、读写互斥）。

```c
semaphore rw = 1;       // 写者与"第一个/最后一个读者"之间的锁
semaphore mutex = 1;    // 保护共享计数 count
int count = 0;          // 当前读者数

读者: P(mutex);
      if (count == 0) P(rw);   // 第一个读者锁门
      count++;
      V(mutex);
      ────── 读文件 ──────
      P(mutex);
      count--;
      if (count == 0) V(rw);   // 最后一个读者开门
      V(mutex);

写者: P(rw);  ── 写文件 ──  V(rw);
```

要点：① 读者**成群**进出，`rw` 由第一个读者 P、最后一个读者 V；② `count` 是普通共享变量，它自身的自增自减也要 `mutex` 保护；③ 此版**读者优先**：只要还有读者到达，写者就一直等，可能**写者饥饿**（写者优先/读写公平是变体，放翻书清单）。

### 7.5 哲学家进餐（防死锁专题）

5 位哲学家围坐，两人间一支筷子共 5 支，必须拿到左右两支才能吃。朴素写法：

```c
semaphore chop[5] = {1,1,1,1,1};
第 i 位: P(chop[i]);  P(chop[(i+1)%5]);  吃饭;  V(chop[(i+1)%5]);  V(chop[i]);
```

所有人同时拿起左筷 → 每个人都等右筷 → **循环等待，全部死锁**（这就是 03 篇死锁四条件的活标本）。三种标准防法：

| 防法 | 做法 | 破坏的条件（03 篇详讲） |
|---|---|---|
| 限制人数 | 加 `room = 4`，拿筷前先 P(room) | 循环等待（至少一人能拿到两支） |
| 奇偶错峰 | 奇数号先左后右，偶数号先右后左 | 循环等待 |
| 同时拿两支 | 左右都可用才用原子操作一次拿走（AND 信号量/管程封装） | 占有并等待 |

## 8. 管程

信号量的 P/V 分散写在每个进程里，顺序错了就死锁。管程把同步逻辑**集中封装**：

- **组成**：管程名称 + 共享数据结构 + 对数据操作的一组过程（方法）+ 初始化语句。
- **核心特性**：**任一时刻最多一个进程在管程内执行方法**——互斥由编译器/语言运行时保证，程序员不再手写 P/V。
- **条件变量** `condition x`：管程内资源暂不满足时用两个操作协调：
  - `x.wait()`：阻塞并**让出管程**，挂到 x 的等待队列；
  - `x.signal()`：唤醒 x 队列中一个进程；**若队列空，signal 什么也不发生（信号不累积）**——这是与 V 操作最大的区别。

| 对比项 | 信号量 | 管程 |
|---|---|---|
| 互斥谁保证 | 程序员自己写 P/V | 编译器保证，每次只进一个 |
| wait/queue | P 一次，计数与队列合一 | 条件变量只排队、**不计数**，空 signal 无效 |
| 出错面 | P/V 分散，顺序错会死锁 | 同步集中在方法内，不易错 |
| 典型语言 | 一切系统 | Java `synchronized`/`wait/notify`、Hoare 管程、Python Condition |

## 9. 模型识别卡（看到题干词 → 套模型）

| 题干特征 | 模型 | 信号量骨架 |
|---|---|---|
| 缓冲区有 n 个位置，放/取两类角色 | 生产者-消费者 | empty=n, full=0, mutex=1 |
| 一个台子放一种特定产品，多个角色各取所需 | 苹果橘子 | plate=1 + 每种产品一个 0 信号量 |
| 一个供应者发不同组合，多个不同等待者 | 吸烟者 | 每消费者一个 offer + 一个 finish |
| "多个人可以同时读，写要独占" | 读者-写者 | rw=1 + 保护 count 的 mutex=1 |
| 环形资源、每人要拿左右两个 | 哲学家进餐 | 必写防死锁三法之一 |
| 只要求"A 的某步在 B 某步之前" | 纯同步 | 一个初值 0 的信号量，前 V 后 P |

## 10. 典型题型与方法

**题型① PV 大题（综合必考）**：数角色列关系 → 设信号量 → 写代码，三步模板见 §6。
入口收尾必查两处：同步 P 是否都写在互斥 P 之前；每个 P 是否都有配对的 V。

**题型② 模型识别**：题干描述 → 对号入座，识别卡见 §9。
入口：先认模型再动笔，模型认错全盘皆错；认不准时数"几类角色 + 几个临界资源 + 几条先后关系"。

**题型③ 信号量 value 判读**：给一段连续 P/V 序列，问 value 值与阻塞进程数。
入口：按执行序列逐条模拟，只盯两件事——value 当前值、等待队列人数；value < 0 时 |value| = 队列长度。

**题型④ "违反哪条准则"判断题**：给一种实现（单标志/双标志/Peterson/关中断/TS/Swap）问缺陷。
入口：拿 §3 四准则逐条对照，先分清是**正确性**问题（忙则等待、空闲让进、有限等待）还是**效率**问题（让权等待）。

**题型⑤ 死锁预判**：给 PV 写法问"会不会永久等待"。
入口：找"P 在等的资源被另一个也在等的进程握着"的环路——生产者-消费者反序 P、哲学家朴素解都是标本；系统化判定（四条件、资源分配图）在 03 篇。

## 11. 易错点

- **互斥 P 写在同步 P 前面**：生产者-消费者的头号死锁写法。死记"**先看有没有资源，再去抢锁**"——同步 P 先、互斥 P 后；V 的顺序无所谓。
- "P 操作一定会阻塞"：错。P 是先 `value--`，减完仍 ≥0 就直接通过；阻塞条件是减完 <0。
- "信号量初值可以设成负数"：错。初值只能是 ≥0 的整数；负值只在运行中出现，其绝对值是等待进程数。
- "V 操作会让信号量一直积累信号"：记录型信号量 V 只唤醒队列；管程的 `signal` 对空队列完全无效，两者别混。
- "读者-写者只需一个 rw 信号量"：漏了保护 `count` 的 mutex；多个读者同时改 count 本身就是竞态。
- "读者越多越乱"：错，读读不互斥，这是该模型允许读者并发的原因；乱在 count 的修改上。
- 双标志**先检查**法违反"忙则等待"（同时进）；**后检查**法违反"空闲让进/有限等待"（都进不去）；Peterson 违反的是"**让权等待**"（自旋），不是正确性条款。
- "关中断能在多核上互斥"：错，只对单处理机有效；TSL/Swap 才支持多处理机，但都是忙等。
- 苹果橘子题中 `plate=1` 已经隐含互斥，再叠床架屋加 mutex 是常见误写（容量 >1 才必须加）。
- 哲学家题**只写朴素拿筷不写防死锁措施**等于没答完，必须给出三法之一并指明破坏的条件。
- PV 是原语、不可中断；但用户态程序调用 P/V 会经内核态阻塞/唤醒，"不可中断"指原语执行的原子性，不是说进程不会阻塞。
- "整型信号量和记录型信号量的 P 是同一种写法"：错。整型是**先判后减**（`while(S<=0); S--;`，忙等自旋），记录型是**先减后判**（`value--` 后 <0 才阻塞入队）。两套伪代码混出时先认是哪种，再谈阻塞与等待队列。
